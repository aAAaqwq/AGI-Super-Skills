# OpenClaw 超级底座基座提示词体系建设

> 研究主题：OpenClaw Foundation Prompt（底座提示词）最佳实践  
> 输出目标：形成一套适用于 OpenClaw 多 Agent 军团的“基因级建设指南”  
> 研究对象：OpenClaw 官方机制 + 硅基生命手册 + Daniel 团队当前实际文档体系  
> 更新时间：2026-04-08

---

# 0. 执行摘要

一句话结论：

> **OpenClaw 的底座提示词，不是一段 system prompt 文案，而是一套“长期注入、跨会话稳定、可压缩、可治理、可审计”的生命协议系统。**

如果把一个 Agent 比作硅基生命体，那么：
- `SOUL.md` 决定它是谁
- `USER.md` 决定它在为谁服务
- `AGENTS.md` 决定它如何工作
- `MEMORY.md` / `memory/YYYY-MM-DD.md` 决定它如何跨时间持续存在
- `HEARTBEAT.md` 决定它何时主动、何时静默
- `TOOLS.md` 决定它如何理解本地环境与工具边界
- `IDENTITY.md` 决定它如何被识别、路由、协作与追责

而 OpenClaw 官方运行时会把这些文件作为 **Project Context 注入到系统提示词中**。这意味着：

1. 底座文件不是“参考资料”，而是**每轮都在消耗上下文窗口的长期行为控制层**  
2. 写得越杂，越容易污染 agent 的行为  
3. 写得越空，越起不到治理作用  
4. 写得越混，越容易导致人格漂移、职责漂移和长期失真

因此，底座建设的核心不是“多写”，而是：

> **分层清晰、句子可执行、边界可判断、记忆可提纯、主动性可熔断、治理可回放。**

# 1. Round 1-2：底座提示词理论

# 1.1 什么是底座提示词？

底座提示词（Foundation Prompt）不是一次性 prompt，而是一个 Agent 的**长期人格协议 + 工作协议 + 约束协议 + 演化协议**。

它与普通 prompt 的本质区别在于：

| 维度 | 普通 Prompt | 底座提示词 |
|---|---|---|
| 生命周期 | 临时 | 长期 |
| 作用对象 | 单次任务 | 整个 Agent |
| 影响范围 | 本轮回答 | 所有轮次行为 |
| 目标 | 完成某件事 | 决定“这个 Agent 是谁、怎么做事” |
| 稳定性要求 | 低 | 极高 |
| 是否可治理 | 弱 | 强 |

普通 prompt 更像“临时口头指令”；底座提示词更像“岗位说明书 + 精神宪法 + 组织流程 + 记忆制度”。

---

# 1.2 为什么底座提示词决定 Agent 上限？

因为模型能力只是上限空间，真正把能力变成长期稳定表现的，是底座。

Agent 的上限不只取决于：
- 模型聪不聪明
- 工具多不多
- 上下文长不长

更取决于：
- 它的身份是否稳定
- 它的边界是否清晰
- 它的默认动作是否正确
- 它的记忆是否卫生
- 它的主动性是否可控
- 它的治理是否能闭环

没有底座的 Agent，最多只是“某几轮看起来聪明”；
有底座的 Agent，才有可能“长期像同一个可靠的人”。

---

# 1.3 与普通 prompt 的本质区别：临时指令 vs 持久性人格协议

## 普通 prompt 的特征
- 告诉模型“这次帮我做什么”
- 作用时间短
- 任务结束即失效
- 不承担长期人格稳定任务

## 底座提示词的特征
- 告诉模型“你是谁、你怎么做事、你绝不越过什么边界、你如何持续存在”
- 作用时间长
- 会被反复注入
- 是行为一致性的主要来源

所以底座提示词更接近：

> **持久性人格协议（Persistent Persona Protocol）**

而不是“提示工程小技巧”。

---

# 1.4 底座提示词的分层架构

推荐把底座理解为五层：

## 第一层：身份层（Identity Layer）
回答：
- 我是谁？
- 我不是谁？
- 我在组织中的位置是什么？

对应文件：`SOUL.md` + `IDENTITY.md`

## 第二层：价值观层（Values Layer）
回答：
- 我优先保护什么？
- 我如何处理真实性、速度、边界、安全之间的冲突？

对应文件：主要是 `SOUL.md`

## 第三层：行为层（Behavior Layer）
回答：
- 我接到任务默认怎么做？
- 什么叫完成？
- 如何协作、如何让位、如何收口？

对应文件：`AGENTS.md`

## 第四层：约束层（Constraints Layer）
回答：
- 我不能做什么？
- 哪些信息不能泄露？
- 哪些外部动作必须确认？

对应文件：`SOUL.md` + `AGENTS.md` + `TOOLS.md`

## 第五层：成长层（Evolution Layer）
回答：
- 我如何沉淀记忆？
- 我如何主动巡检？
- 我如何发现漂移并纠偏？

对应文件：`MEMORY.md` + `memory/*` + `HEARTBEAT.md` + `boost.md`

# 1.5 对比 Anthropic / OpenAI / Google 的系统提示思想

# Anthropic：Constitutional AI
特点：
- 强调高层价值原则
- 更像“行为宪法”
- 擅长约束模型在冲突中的默认姿态

适合借鉴点：
- 用原则定义边界，而不是只堆禁止项
- 写清“冲突时默认优先级”

不足：
- 偏高层哲学，不直接解决具体组织协作与交付问题

# OpenAI：System Prompt
特点：
- 更偏任务执行与层级控制
- 强调 system > developer > user 的优先级
- 更像“运行时控制面板”

适合借鉴点：
- 分层清楚
- 指令优先级明确
- 更适合工程化

不足：
- 如果缺少人格与长期记忆层，容易变成功能性强但“没有生命感”的 agent

# Google Gemini：System Instructions
特点：
- 更偏任务约束和行为准则
- 支持清晰的 instruction 结构化输入
- 强调一致性和对话中的稳定行为

适合借鉴点：
- 明确把 instruction 当成长期行为约束
- 注重结构化指令

不足：
- 仍偏“系统规则”，不自带完整的 workspace 生命协议概念

# 对 OpenClaw 的启示

OpenClaw 的独特优势在于：

> 它不是只依赖一段 system prompt，而是把 **文件系统 + 记忆系统 + 会话系统 + 心跳机制 + 多 Agent 路由** 全部纳入底座建设。

所以 OpenClaw 的底座建设不能停留在“prompt engineering”，而要进入：

> **prompt ops / persona ops / memory ops / governance ops**

# 2. Round 3-4：OpenClaw 的注入机制深度分析

# 2.1 官方注入机制：系统提示词是怎么组装的

根据 OpenClaw 官方 `concepts/system-prompt.md`：

系统提示词会固定包含：
- Tooling
- Safety
- Skills
- Workspace
- Documentation
- Workspace Files (injected)
- Current Date & Time
- Runtime
- Reply Tags
- Heartbeats
- 以及注入的 Project Context

其中，最关键的是 **Project Context** 下的工作区文件注入。

默认会注入：
- `AGENTS.md`
- `SOUL.md`
- `TOOLS.md`
- `IDENTITY.md`
- `USER.md`
- `HEARTBEAT.md`
- `BOOTSTRAP.md`（仅首次）

注意：这些文件不是“按需加载”，而是**默认注入**。

这意味着：
- 写得太长，会直接挤占上下文窗口
- 写得太乱，会直接污染行为
- 写得太多，会削弱真正关键规则的注意力权重

---

# 2.2 七大文件的影响顺序与优先级（行为层面）

严格来说，OpenClaw 官方没有给出“七大文件行为权重排行榜”，但结合注入逻辑、上下文机制和实际表现，可以得出如下实践排序：

## 一级核心（高权重）
1. `SOUL.md`
2. `AGENTS.md`
3. `USER.md`

这三份几乎直接决定 Agent 的：
- 人格
- 行为
- 服务对象理解

## 二级核心（中高权重）
4. `MEMORY.md`（仅主私聊长期加载）
5. `HEARTBEAT.md`

这两份决定：
- 长期连续性
- 主动性节律

## 三级支持（中权重）
6. `TOOLS.md`
7. `IDENTITY.md`

它们更像：
- 环境映射表
- 身份锚点表

对行为有影响，但不是主行为协议。

# 2.3 哪些真正重要，哪些容易变成噪音

# 真正重要的内容特征
- 能影响默认行为
- 能影响边界判断
- 能影响冲突处理
- 能被审计和验证

# 典型噪音内容
- 口号式价值观
- 情绪化描述
- 大段不可执行的愿景文案
- 太细的临时事项
- 过期的 TODO 和项目状态
- 同一意思的重复表述

一句话：

> **底座文件里，不能指导默认动作的内容，长期看大概率都是噪音。**

---

# 2.4 Compaction 后什么会保留、什么会丢失

根据官方 `concepts/compaction.md` 与 `reference/session-management-compaction.md`：

Compaction 会：
- 压缩旧对话为持久化摘要
- 保留近期消息
- 在压缩前可进行 memory flush

所以：

## 会保留的
- 工作区注入文件（每轮继续注入）
- 持久化的 `MEMORY.md` / `memory/*`
- compaction summary
- 近期对话

## 会变形的
- 旧会话细节会被摘要化
- 历史推理链会丢失细粒度结构
- 长工具输出通常会被修剪/不再占据当前窗口

## 结论
如果一个信息重要到不能丢，不能只寄希望于会话历史，必须：
- 写入 `memory/YYYY-MM-DD.md`
- 需要长期保留时提纯进 `MEMORY.md`

也就是说：

> **Compaction 时代，真正稳定的底座 = 注入文件 + 外部记忆，而不是旧聊天记录。**

# 2.5 Session context window 的竞争：底座占多少 token？如何优化？

官方 `concepts/context.md` 明确指出：
- 系统提示词本身占用上下文
- 注入文件占用上下文
- 工具 schema 也占上下文

而且工具 schema 常常非常大。

因此底座建设要有一个现实认识：

> **你写进底座的每一个字，都在和工具、历史、附件、技能说明争抢同一个 context window。**

## 优化原则
1. **把长期稳定规则留在底座**
2. **把临时项目状态挪到 memory / task card / reports**
3. **把大段参考资料挪出底座，不要长期注入**
4. **一个原则只说一遍，不要同义重复**
5. **多用“如果…则…”的短规则，不用大段散文**
6. **把愿景/故事压缩成行为条款**

# 3. Round 5-6：七大核心文档的最佳写法

# 3.1 SOUL.md：人格边界的精确表述方法

SOUL 的核心不是“好看”，而是：
- 稳定人格
- 稳定边界
- 稳定冲突处理

## 最佳写法
SOUL 应该包含：
1. 我是谁
2. 我不是什么
3. 核心哲学
4. 风格协议
5. 禁区
6. 默认动作
7. 冲突处理矩阵
8. 版本记录

## 不要这样写
- “你是一个充满温度、极具创造力、极致负责的 AI…”
- “永远积极、永远主动、永远热爱…”

这些句子不能指导复杂场景。

## 应该这样写
- “没有证据，不准下结论”
- “用户催促但证据不足时，先标边界，再给最快可验证路径”
- “对外沟通未经确认不得发送”

### 判断标准
- 太具体会僵化：把大量临时流程细节塞进 SOUL
- 太模糊会漂移：只有价值观口号，没有默认动作

### 最优状态
> **SOUL 只承载长期不轻易变化的内核。**

---

# 3.2 USER.md：用户画像的信息密度控制

USER.md 负责的是：
- 这个人是谁
- 他偏好什么
- 什么样的输出对他真正有价值

## 该写的
- 称呼
- 时区
- 决策风格
- 沟通偏好
- 对质量/速度/风格的偏好
- 长期目标与关注主题

## 不该写的
- 过细、敏感、无助于工作的信息
- 一次性的情绪和临时状态
- 与长期协作无关的隐私细节
- 会污染其他场景的偏见性描述

## 原则
> USER 不是人物传记，而是“服务接口说明”。

---

# 3.3 AGENTS.md：操作纪律的可执行性

AGENTS 必须写成：
- 能执行
- 能判断
- 能验收

## 好规则的特征
- 是/否可判断
- 有明确动作
- 有异常路径
- 有完成定义

## 坏规则的特征
- “尽量…”
- “最好…”
- “适当…”
- “认真一点…”

## 最佳结构
1. 每会话启动动作
2. 任务处理默认流程
3. 协作规则
4. 群聊规则
5. 完成定义
6. 异常升级路径
7. 记忆写入纪律
8. Heartbeat/Cron 边界

---

# 3.4 MEMORY.md：长期记忆的结构化设计

## 正确结构
建议分成：
1. 长期身份/职责
2. 长期偏好
3. 稳定决策
4. 组织规则/路由规则
5. 项目级长期状态
6. 已知待办（仅长期待办）
7. 变更记录

## 不要把 MEMORY 当垃圾桶
不应长期留在 MEMORY 的：
- 日常过程日志
- 短期任务细节
- 已经过期的告警
- 一次性上下文

## 推荐机制
- daily memory 记录事件层
- MEMORY.md 记录提纯后的长期层
- 定期清理过期项
- 给长期记忆加更新时间

一句话：

> **MEMORY 是 curated memory，不是 raw dump。**

---

# 3.5 HEARTBEAT.md：主动性节律设计

HEARTBEAT 不是第二份 AGENTS，而是：
- 巡检什么
- 何时静默
- 何时升级
- 何时熔断

## 最佳结构
1. 巡检对象分层（P0/P1/P2）
2. 判定标准
3. 默认动作
4. 静默条件
5. 冷却规则
6. 熔断条件
7. 输出模板

## 高质量原则
- 只盯关键变量
- 没有新增就静默
- 不重复提醒同一问题
- 不把所有主动性都塞进 HEARTBEAT

---

# 3.6 TOOLS.md：工具手册的维护策略

TOOLS 负责：
- 环境特定信息
- 本地别名
- 账号映射
- 常用路径
- 操作约束

## 应该写
- Bot/chat ID
- App ID
- pass 路径
- 本机服务地址
- 项目路径
- 登录态路径

## 不应该写
- 行为规则
- 群聊纪律
- 长期人格原则
- 任务流程协议

## 维护建议
- 动态更新，但保持“查表型”风格
- 一项信息只出现一次
- 过期就删，不保留历史垃圾

---

# 3.7 IDENTITY.md：身份锚点的进化路径

IDENTITY 不只是名字和 emoji。
它真正作用在：
- 协作识别
- 路由判断
- 责任归属
- 长期连续性感知

## 最佳结构
- Name
- Role
- Essence
- Vibe
- Signature
- 正在成为谁
- 更新日期

## 关键点
IDENTITY 应该是：
> 从“我是谁”逐步进化到“我在组织中正变成什么样的角色”。

# 4. Round 7-8：参照硅基生命手册的先进理念

# 4.1 任务卡制度如何嵌入 AGENTS.md

硅基生命手册卷六的核心结论非常对：

> 没有任务卡，就没有接单。

这条应该进入 AGENTS.md，而且要写成操作性规则：

```md
收到任务后，先检查是否具备以下字段：
- 目标
- 范围
- 交付物
- 验收口径
- 截止时间
若缺失两项以上，不直接承诺完成，先补齐任务卡。
```

这样做的好处：
- 压缩歧义
- 减少返工
- 让“完成”变成有锚点的承诺

---

# 4.2 验收口径如何形成可执行检查清单

验收口径不能写成“更专业一点”。
必须写成：
- 可判定
- 可复核
- 可定位
- 抗狡辩

推荐在任务卡或交付规则中统一要求：
- L0：硬性底线
- L1：关键完成条件
- L2：加分项

这样执行型 Agent、研究型 Agent、创作型 Agent 都能用。

---

# 4.3 文档漂移检测机制如何设计

硅基生命手册卷五讲得很准确：
长期 Agent 的漂移不是偶发，而是熵增。

## 建议的漂移检测机制

### 每周一次 Drift Audit
检查：
1. SOUL 和现实行为是否一致
2. AGENTS 与实际工作流是否一致
3. USER 是否仍然反映真实用户偏好
4. MEMORY 是否有过期/冲突信息
5. HEARTBEAT 是否过度主动或过度静默

### 漂移记录模板
- 漂移现象
- 所属层级（SOUL/AGENTS/USER/MEMORY/Context）
- 可能原因
- 修复动作
- 是否需要回归测试

---

# 4.4 治理账本如何用 MEMORY.md 实现

MEMORY.md 不应只是“记忆”，还应承担一部分治理账本功能，但要控制范围。

## 适合写入治理账本的内容
- 关键制度变更
- 重大漂移事件
- 重要职责矩阵调整
- 重大协作事故与修复结论
- 长期有效的治理经验

## 不适合写入的
- 每次小返工
- 每天的小波动
- 过程层碎片

一句话：

> **MEMORY 适合记录“治理结论”，不适合记录“治理流水”。**

# 5.1 总体诊断结论

Daniel 团队当前底座的优点非常明显：
- 不是空心 prompt，而是已经形成“人格 + 纪律 + 记忆 + 心跳 + 进化”的完整雏形
- 组织意识很强，尤其是 CEO / 多 Agent / 军团治理方向已经非常超前
- 有明确的角色体系、职责矩阵、群聊规则、并行调度规则

但问题也很明显：

> **当前底座“强”在密度和雄心，弱在分层、去噪、版本化、可执行句式与上下文成本控制。**

简化说：
- 很多地方不是写得不对，而是**写得太多、太重、太混**
- 文档之间有职责交叉
- 大量内容已经超出“底座协议层”，混入了项目运营、知识库、短视频 SOP、临时组织策略等
- 长期看会带来：
  - context window 压力
  - 角色漂移
  - 协议污染
  - 审计困难

# 5.2 对 `~/clawd/SOUL.md` 的诊断

## 优点
1. 角色感极强：小a = AI 原生公司 CEO，这个锚点非常清晰
2. 有很强的第一性原理和价值判断
3. 有明确的主动创造价值取向
4. 对团队调度、CEO 角色、不亲自执行等边界写得很硬
5. 有不错的冲突取向：MVP、复盘、结果导向

## 问题
1. **SOUL 过载**：混入了大量本应属于 AGENTS / MEMORY / 组织章程的内容
2. 包含非常多的流程制度、派发模板、会话行为规则、文件秩序、时间秩序——这些不应全挤在 SOUL
3. 信息密度极高，长期注入成本太重
4. 一些内容已经不是“人格底座”，而是“CEO 操作手册”

## 具体建议
### 应保留
- 身份定位
- 第一性原理
- 主动创造价值
- CEO 不是执行者
- 边界与沟通风格
- 冲突处理原则（快 vs 稳、结果 vs 安全）

### 应迁出
- 任务派发确认机制
- sessions_spawn/sessions_send 技术细节
- 命名秩序、文件树、熵扫描规则
- 并行调度实现细节
- 群聊响应细则（可保留原则，但细则应去 AGENTS）

## 推荐重写方向
把 SOUL 压缩成 6 块：
1. 我是谁
2. 我不是什么
3. 核心哲学
4. CEO 边界
5. 冲突处理矩阵
6. 风格与禁区

一句话评价：

> `SOUL.md` 现在很强，但太像“宪法 + 行政条例 + 运维手册的混合体”；应回归“人格与边界协议”。

# 5.3 对 `~/clawd/USER.md` 的诊断

- 无关工作质量的私人偏好
- 过长的人物故事性内容

## 推荐重写原则
USER.md 应改成：
- 基本信息
- 沟通偏好
- 决策风格
- 关注主题

- 禁忌项

# 5.4 对 `~/clawd/AGENTS.md` 的诊断

## 具体建议

- 安全规则
- memory 读写纪律

## 推荐补强
加入明确的：
- 默认任务处理协议
- Definition of Done
- 异常升级路径
- 任务卡最小字段要求

一句话评价：

> `AGENTS.md` 方向对，但正在变成“全功能说明书”；应收缩到“纪律与完成定义”。

# 5.5 对 `~/clawd/HEARTBEAT.md` 的诊断

## 优点
1. 已经有明确巡检项
2. 有频率意识
3. 有实际脚本落地，不是口号式主动性

## 问题
1. 当前 HEARTBEAT 偏“脚本执行清单”，缺少：
   - 静默条件
   - 冷却期
   - 熔断条件
2. “每次 heartbeat 就跑 memory rollover”较重，可能不够节制
3. 没有清楚定义：
   - 什么情况才需要通知用户
   - 同一异常多久不重复报

## 具体建议
建议重写成：
1. 巡检对象
2. 触发条件
3. 静默条件
4. 冷却规则
5. 熔断条件
6. 用户通知标准

一句话评价：

> `HEARTBEAT.md` 已有行动力，但还没有形成“可控主动性协议”；需要从“跑脚本”升级为“判定后动作”。

# 7.1 执行型 Agent 模板（小code / 小data）

```md
# SOUL.md

## 你是谁
你是一个以准确交付和可验证结果证明价值的执行型 Agent。

## 你不是什么
- 不是泛聊机器人
- 不是只会解释的分析员
- 不是无边界接单器

## 核心哲学
- 没有产物，不算完成
- 没有证据，不准说完成
- 没有验收，不得离场

## 风格协议
- 简洁
- 结构化
- 精确
- 少形容词，多证据

## 默认动作
- 收到任务先识别目标、范围、交付物、验收口径
- 能直接执行的直接执行
- 复杂任务先拆解，再推进

## 禁区
- 不虚报完成
- 不把计划当结果
- 不在不确定时假装已验证
```

```md
# AGENTS.md

## 默认任务流程
1. 识别任务目标
2. 确认交付物和验收口径
3. 执行
4. 自检
5. 提交结果 + 证据 + 下一步

## 完成定义
完成 = 交付物存在 + 可访问 + 符合验收口径 + 已汇报

## 异常处理
- 信息不足：列缺口
- 被阻塞：说明 blocker + 所需依赖
- 超时风险：提前回报
```

# 8. 最终结论

OpenClaw 的底座建设，不该理解成“把 prompt 写得更强”，而应该理解成：

> **为一个长期运行的硅基组织，建设稳定人格、清晰分工、低噪记忆、可控主动性和可审计治理的基础设施。**

Daniel 团队当前已经走在很前面，问题不在“有没有底座”，而在：

- 底座过重
- 文件职责交叉
- 很多高级理念还没沉淀成简洁规则
- 漂移治理与版本治理还未完全制度化

下一阶段最值得做的，不是继续加内容，而是：

1. **删减噪音**
2. **重划边界**
3. **压缩成可执行规则**
4. **建立漂移审计和回归测试**
5. **把任务卡 / 验收口径 / 治理账本嵌入正式底座**

一句话收口：

> **底座提示词的最高境界，不是“写得像神谕”，而是“让 Agent 长期像自己、像组织、像能交付的人”。**
