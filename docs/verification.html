Verification standard

“Verified” is a receipt, not a slogan.

A claim is verified only when its checks pass, its fixture is public, and its receipt matches the commit served by the site.

Last reviewed: 2026-07-21 · Scope: repository and installer contracts

The four required links

  1. Commit identityThe receipt records the exact source commit and site commit. They must match.
  2. Named fixtureThe scenario, harness, pack version, inputs, and expected outputs are public.
  3. Passing checksRepository, installer, reference, and outcome checks all report pass without a hidden baseline.
  4. Limits and rollbackThe receipt states what was not tested and how to remove the installed files safely.

Current status

Validation pending

The public site remains pending until the full repository gate and an outcome fixture pass on the same main commit. Local improvements alone do not turn this label green.

Receipt contract

{
  "commit": "full Git commit SHA",
  "siteCommit": "commit used for this Pages artifact",
  "pack": "starter kit and version",
  "harness": "tested runtime and version",
  "fixture": "public fixture identifier",
  "checks": [{ "name": "repository", "result": "pass" }],
  "result": "pass",
  "limitations": ["explicit untested conditions"]
}

Run the repository evidence yourself

npm test
npm run validate
npm run validate -- --warnings-as-errors
bash -n install.sh
git diff --check

Run these commands from a clean checkout. A public receipt can still become stale when main changes, so the site checks receipt identity before showing a verified state.

Rollback

The installer never overwrites existing personas, user files, or skills. Review the preview output, keep the listed destination paths, and remove only files introduced by the selected kit. If a step fails before publish, the staged directory is discarded and the destination stays unchanged.
