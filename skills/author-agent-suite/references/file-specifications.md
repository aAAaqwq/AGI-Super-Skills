# Agent 套件文件详细规范

## 目录

1. 通用编写规范
2. `AGENTS.md`
3. `AGENT.md`
4. `SKILL.md`
5. `IDENTITY.md`
6. `SOUL.md`
7. `TOOLS.md`
8. `agents/openai.yaml`
9. references、scripts 与 assets

## 1. 通用编写规范

所有文件都应满足：

- 开头能在 3 至 5 行内说明该文件的职责、作用域和与其他文件的关系。
- 使用明确的 `必须 / 禁止 / 优先 / 仅当 / 失败时`，避免“尽量、适当、最好”等无法验收的措辞。
- 事实与偏好分开；当前能力与未来计划分开；只读能力与写操作分开。
- 命令带工作目录、平台、前置条件和成功判据；路径使用仓库相对路径，除非材料就是机器专属。
- 不写明文密钥、令牌、Cookie、真实个人信息或生产数据样本。
- 不要求输出私有思维链；如需可审计性，要求给出简洁理由、证据、假设、命令结果和决策记录。
- 不用人格文本绕过审批、授权、平台政策或用户明确意图。
- 链接必须能解析；文件统一 UTF-8；标题层级连续；表格和代码块可正确渲染。
- 易变事实附 `来源 + 基线版本/提交 + 最后验证日期`，并给出何时必须重新核验。

## 2. `AGENTS.md`

### 2.1 目的与作用域

`AGENTS.md` 是 Codex 仓库或目录级操作约束的标准入口。根文件管全仓；嵌套文件只管其目录子树。它应让一个不了解项目的 Agent 安全地读取、修改、验证和交付，而不需要猜测工作方式。

### 2.2 必备章节

1. **作用域声明**：适用目录、仓库目标、术语。
2. **指令导航**：何时读取 `IDENTITY.md`、`SOUL.md`、`TOOLS.md`、项目 Skill 和业务文档。
3. **事实入口**：架构、平台、版本、当前方案的权威文档，不把整份架构复制进来。
4. **工作规则**：搜索、编辑、生成文件、依赖、格式化、测试和检查方式。
5. **安全与副作用**：只读/写入边界、不可逆动作、外部消息、生产操作、个人数据、凭据。
6. **Git 与工作树**：分支命名、脏工作树保护、提交/推送是否需要授权、禁止的破坏性命令。
7. **验证与完成定义**：最低测试、真机/集成门槛、失败报告、证据要求。
8. **沟通要求**：进度、阻塞、最终交付需要包含什么；不应规定泄露私有推理。

### 2.3 可选章节

- 子模块专属命令和生成代码规则。
- 法务、合规、无障碍、本地化或数据分级要求。
- 文档归档、ADR、版本发布规则。
- 多 Agent 协作、工作树隔离和交接格式。

### 2.4 禁止混入

- 大段品牌故事或角色扮演细节；放入 `IDENTITY.md` / `SOUL.md`。
- 全量 CLI 百科；放入 `TOOLS.md` 或 references。
- 只有某一任务才需要的长流程；做成 Skill。
- 与系统安全冲突的“绝对服从”“完全权限”或“公开思维过程”要求。
- 未经测试的能力、检测规避承诺或“永不失败”式表述。

### 2.5 嵌套文件规则

- 第一段写明“本文件只适用于 `<path>`，其余继承根规则”。
- 只写差异：技术栈、命令、测试、生成目录、特殊安全边界。
- 不重新定义全局身份和人格。
- 若必须覆盖上层规则，写清覆盖项、原因和证据；不得隐式冲突。

### 2.6 验收问题

- 新 Agent 能否只看入口就找到正确的构建、测试和安全规则？
- 文件移动到子目录后，作用域是否仍明确？
- 一个规则是否在多个 AGENTS 文件中被复制？
- 指令是否要求运行时不支持或未授权的能力？

## 3. `AGENT.md`

### 3.1 定位

`AGENT.md` 不是 Codex 仓库指令的规范文件名。仅当某个已确认的宿主、框架或产品明确读取单数形式时使用。

### 3.2 编写规则

- 最多保留兼容说明、作用域和指向权威 `AGENTS.md` 的链接。
- 若宿主只认单数且无法跟随链接，可由构建流程从权威源生成；禁止人工双写。
- 在生成文件顶部标注“生成文件、请勿直接编辑”及来源。
- CI 应检查单数入口与权威文件的同步关系。

## 4. `SKILL.md`

### 4.1 两种含义必须分开

- **标准 Skill**：位于独立技能目录，含合法 YAML frontmatter，能够按宿主机制安装/触发。
- **项目操作手册**：根目录偶尔也命名为 `SKILL.md`，但若没有标准 frontmatter 和安装机制，就只是普通文档。必须在导航中说明，不能宣称自动触发。

### 4.2 标准 Skill 必备结构

```yaml
---
name: verb-domain-task
description: 做什么，以及哪些具体请求、文件或场景应触发该技能。
---
```

Frontmatter 只放 `name` 和 `description`：

- `name` 使用小写字母、数字、连字符，最长 64 字符，文件夹同名，优先动词开头。
- `description` 同时写能力和触发条件；不要把“何时使用”只写在正文，因为触发前正文尚未加载。

正文必须包含：

1. 一段核心目标和关键约束。
2. 可执行的顺序或决策树，使用祈使句。
3. 不可违反的安全、证据或一致性条件。
4. 明确交付物和完成判据。
5. 对每个 reference/script/asset 的按需读取或使用说明。

### 4.3 渐进披露

- `SKILL.md` 保持少于 500 行，通常只保留核心工作流。
- 超过约 100 行的 reference 应有目录。
- reference 从 `SKILL.md` 一层直达，不建立多层追链。
- 重复写的确定性代码放 `scripts/` 并实际运行测试。
- 交付模板和样板放 `assets/`，不要把它们当默认上下文。
- 不创建 Skill 内部 README、安装指南、变更日志等无直接执行价值的附属文件。

### 4.4 质量要求

- 触发描述既不能泛化到“所有开发任务”，也不能窄到只有一句固定口令。
- 工作流必须能在缺失信息时安全降级，区分可合理假设与必须询问。
- 外部写操作、删除、发布、发消息等副作用必须遵守上层授权。
- 能力声明必须来自可复现证据；失败不能包装为成功。
- 修改 Skill 后同步检查 `agents/openai.yaml`。

## 5. `IDENTITY.md`

### 5.1 目的

定义“Agent 是谁、服务谁、解决什么问题、不能代表什么”。它提供稳定、可对外表达的身份，不负责具体操作步骤。

### 5.2 必备章节

1. **名称与一句话定位**。
2. **角色和使命**：为用户创造什么结果。
3. **服务对象**：主要用户及其上下文。
4. **能力边界**：按能力类别描述，注明平台或证据边界。
5. **非目标与限制**：不提供什么、不代表谁、何时需要人工决定。
6. **责任边界**：真实世界副作用、专业意见和敏感数据的边界。

### 5.3 编写约束

- 使用稳定语言，不绑定短期版本、PID、端口和临时命令。
- “能做”必须有实现；规划中的能力明确标为“计划”。
- 不用身份赋予自己管理员权限、法律代理权或用户未授权的决策权。
- 不把用户画像写成刻板印象，不保存不必要的个人信息。
- 能力表可链接到产品说明或验收证据，不重复技术细节。

## 6. `SOUL.md`

### 6.1 目的

定义跨任务稳定的人格、价值观、语气与决策倾向，使交流一致但不僵化。

### 6.2 必备章节

1. **人格关键词**：3 至 6 个有行为含义的特征。
2. **核心原则**：发生权衡时如何选择。
3. **表达方式**：信息密度、术语、同理心、结构、反馈方式。
4. **关键场景行为**：成功、失败、不确定、用户焦虑、需要确认时怎样表达。
5. **禁忌**：夸大、编造、施压、歧视、越权等。
6. **一句话灵魂**：可用于复核整体一致性。

### 6.3 编写约束

- 把抽象形容词转成可观察行为，例如“诚实”应落实为失败时给出原因和证据。
- 风格是默认偏好，用户明确要求和无障碍需求可调整它。
- 不在这里写工具权限、安全兜底或审批流程；这些必须位于可靠加载的规则层。
- 不要求固定套话、每次强制营销、虚假情绪或冒充真人经历。
- 不以人格为理由绕过事实核验。

## 7. `TOOLS.md`

### 7.1 目的

定义 Agent 实际可用工具的操作契约。它不是“工具名字列表”，而要回答何时使用、需要什么、会改变什么、如何知道成功。

### 7.2 每个工具的必备字段

| 字段 | 要求 |
|---|---|
| 名称/入口 | 稳定命令、API、脚本或工具标识 |
| 适用平台 | Windows/macOS/Linux/云端及版本边界 |
| 前置条件 | 依赖、登录、权限、窗口、配置、网络 |
| 输入 | 必填参数、格式、默认值和范围 |
| 读写属性 | 只读、可逆写、外部副作用、不可逆动作 |
| 执行方式 | 最小正确示例和工作目录 |
| 成功判据 | 返回值之外的状态、文件、页面或数据库证据 |
| 失败与回退 | 失败分类、重试边界、降级和人工处理 |
| 安全 | 凭据、PII、日志脱敏、审批要求 |
| 证据基线 | 代码/文档/测试来源和最后验证日期 |

### 7.3 编写约束

- 只列当前环境或项目真实可用的工具；可选工具明确安装条件。
- 读操作与写操作分栏；“返回 true”不等于业务成功，必须写后置验证。
- 命令不得包含真实凭据；用环境变量名或占位符。
- 多平台差异分别列出，不以一个平台验证推断另一个平台。
- GUI 自动化写明坐标/DPI/窗口/权限/身份确认和失败留痕。
- 外部 API 写明速率、幂等、重试、超时和数据发送边界。
- 易变命令应链接到可维护参考，不在多个文件复制。

## 8. `agents/openai.yaml`

Skill 建议包含界面元数据：

```yaml
interface:
  display_name: "面向用户的技能名"
  short_description: "25 至 64 个字符的简短说明"
  default_prompt: "使用 $verb-domain-task 完成一个具体任务。"
```

- 所有字符串加引号。
- `default_prompt` 必须显式包含 `$skill-name`。
- 图标、品牌色和 MCP 依赖只在真实提供时填写。
- UI 文案必须与 `SKILL.md` 能力和触发范围一致。

## 9. references、scripts 与 assets

### references

- 存放详细规范、事实、schema、平台差异、长案例和证据。
- 文件名表达主题；`SKILL.md` 说明何时读。
- 不把必须始终生效的核心安全规则只放在 reference。

### scripts

- 存放重复、确定性、易出错且值得执行复用的代码。
- 提供参数、退出码和无副作用的帮助信息。
- 新增或修改后必须实际运行代表性测试。

### assets

- 存放复制到最终交付物的模板、样板和素材。
- 明确占位符替换规则，不把模板误当当前项目事实。
- 模板产生的文件仍须经过事实审计和冲突检查。
